## 一、背景与结论摘要

本轮审查起因是用户实际遇到的一个体验问题：**在聊天页用右侧时间轴跳转到很早的历史消息时，偶发加载出错误/错位的内容，必须刷新页面才能恢复**。围绕这个问题逐步扩展到消息分页、导出、任务调度与前端基础设施的完整审查。

**总体结论**：

1. 时间轴跳转的"错乱"不是玄学，定位到 **4 个真实缺陷**（§二），其中 2 个（跳转窗口算错、响应竞态）几乎可以确定就是用户遇到的现场。
2. 导出链路整体可用，但存在 **1 个用户可感知的死链 bug**（§四.1）、**"导出所选"的语义陷阱**（§四.2），以及聊天导出与朋友圈导出之间明显的质量落差。
3. 前端基础设施有 **1 个结构性 XSS 隐患**（`esc()` 不转义引号——它已造成现存功能 bug：插件 choice 设置项下拉选项静默丢失，且远端链接 URL 已进入属性位，见 F-1）和 **2 个性能/竞态问题**（模块缓存失效、路由竞态）。
4. v5.0.3 审计中"四处缓存无锁"的结论在 v5.0.6 已部分失效：`api_chat.py` 三处已加锁，**仅剩 `media.py` 的 `_IMG_CACHE` 仍无锁**（§六）。
5. Rust 迁移经评估后**决定不做**（§七），理由与结论一并记录。

**修复优先级总表**见 §八。

## 三、聊天页时间轴跳转缺陷（用户实际遇到的问题）

用户描述的现象：打开与某人的会话 → 右侧时间轴看到最新/最旧月份 → 点最旧的日期跳转 → 偶发显示的不是该时间的内容，像"旧缓存"，必须刷新才恢复。逐行审查 `siwx/ui/pages/chat.js` 与 `api_chat.py` 分页端点后，确认以下 4 个缺陷共同构成该现象。

### J-1【高】跳转窗口的"当天结束时间"计算错误

**位置**：`siwx/ui/pages/chat.js:550`

```js
const endOfDay = ts + 24 * 3600;   // ts 是当天第一条消息的时间戳（first_ts）
```

时间轴日期按钮传给 `jumpToTime` 的是**当天第一条消息的时间戳**（`renderTimelineDays` 里 `data-ts="${d.first_ts || 0}"`，`chat.js:535`），而不是当天零点。因此 `endOfDay = first_ts + 24h` 不是"当天 24:00"，而是"当天第一条消息时刻 + 24 小时"。

**后果示例**：点击 3 月 5 日，那天第一条消息发于 10:00，跳转窗口变成"3 月 6 日 10:00 之前的最后 80 条"——6 日凌晨至 10 点的消息全部挤进窗口。若 6 日上午消息超过 80 条，3 月 5 日的消息会被**整个挤出窗口**，一屏全是没点的那天的内容。

代码里对"窗口内找不到目标"有兜底（`chat.js:554-555`）：找不到 `ts >= 跳转目标` 的行就取 DOM 中第一条消息行——消息按时间升序渲染，即高亮**当前页最旧一条**。不过该兜底实际很难触发：`before = first_ts + 24h` 的窗口几乎总能覆盖当天首条消息，`find()` 通常会命中同日或次日的某一行。用户看到的"点旧日期出现别的时间的内容"，主因是本条的窗口算错把后一天挤进窗口，再叠加 J-2 的竞态。

**修复方向**：由日期字符串 `YYYY-MM-DD`（`d.day`——需一并写入按钮 dataset，当前按钮只传了 `data-ts`）计算**次日零点**（或当天 23:59:59）的时间戳传给 `before`，不使用 `first_ts + 86400`。前端 `new Date(y, m, d+1)/1000` 与服务端 SQLite `localtime` 同为本机时区，语义一致（server 与浏览器同机）。纯前端修改。

### J-2【高】跳转请求无竞态保护，旧响应覆盖新页面

**位置**：`siwx/ui/pages/chat.js:324-358`（`loadMessages`）、`:548-561`（`jumpToTime`）、`:151-163`（滚动加载监听器）

`loadMessages()` 没有请求序号守卫，也没有 AbortController。`jumpToTime` 既不检查也不设置 `loading`（`loading` 只在滚动监听器自身置位，`chat.js:154`），且只重置 `earliest`、**不重置 `hasMore`**（`chat.js:552`）。交错场景：

1. **快速连点两个日期**（或双击）：两个跳转请求同时在飞，后返回者覆盖屏幕。若先点的请求后返回，用户看到的是上一次点击的内容。
2. **跳转 × 滚动加载竞态**：`jumpToTime` 先把消息区换成 loading 提示（`scrollTop` 随之被钳到 0）；若此刻 `hasMore` 仍为 true，滚动监听器会再发出一个 `before=0`（取最新一页）的请求，形成三方并发。真正产生错乱的交错是：**滚动加载请求在点击日期之前 / `await` 期间起飞**（携带旧游标 `earliest`，或因 `earliest=0` 而携带 `before=0`），其响应在跳转渲染之后返回，走 `else` 分支（`chat.js:348-353`）把另一段游标区域的消息 `mergeMessages` + `insertAdjacentHTML('afterbegin', ...)` 插进刚跳转的页面——`loadedMessages` 与 DOM 混入两段不相邻的内容，`earliest`/`hasMore` 也被带错。而跳转**完成之后**由 `scrollIntoView({behavior:'smooth'})` 触发的顶部加载，因游标已是新值，属正常的向前续页，并不损坏。

刷新能恢复，正是因为刷新重置全部状态重新拉第一页——与用户描述完全吻合。

**修复方向**：给 `loadMessages` 加请求代数（序号）：每次 `fresh` 加载递增序号，响应返回时若序号非最新则丢弃；`jumpToTime` 期间置 `loading = true`。仅改 `chat.js`。

### J-3【中】分页游标只看时间戳，同一秒的消息会被永久跳过

**位置**：`siwx/api_chat.py:618`（`WHERE create_time < ?`）、`siwx/ui/pages/chat.js:354`（`earliest = loadedMessages[0].ts`）

向上翻页用 `before = 已载入最早一条的 ts`，服务端取 `create_time < before` 的最新 N 条。如果翻页边界恰好落在一批**同一秒发送的消息**中间（连发消息、消息与系统提示同秒很常见），同一秒内未带出的那几条永远无法被 `<` 条件命中——时间线中段静默缺消息，怎么翻都翻不出来。

**修复方向**：游标升级为 `(ts, local_id)` 组合。服务端 `WHERE (create_time, local_id) < (?, ?)`（或等价的 OR 展开），前端 `before` 同时传两个字段。向后兼容：保留 `before` 语义不变，新增 `before_id` 参数。

### J-4【低】跳转落点会被图片懒加载挤偏

**位置**：`siwx/ui/pages/chat.js:557-558`、图片 `loading="lazy"`（`chat.js:440`）

跳转定位靠一次性 `scrollIntoView`，而消息图片懒加载后内容高度持续变化，滚动结束时目标行已不在原地。打开会话场景有"贴底跟随"机制处理同类问题（`startBottomFollow`，`chat.js:288-318`），跳转场景没有对应重新定位逻辑。

**修复方向**：跳转后监听目标行附近图片的 `load` 事件，加载完成后把目标行重新滚回视野中心；或跳转渲染时临时取消懒加载。

## 四、消息查看链路（跳转之外）

### V-1【中·数据正确性】`is_me` 判定使用 `split("_6")[0]` 脆弱解析

**位置**：`siwx/api_chat.py:481`、`siwx/api_chat.py:600`、`siwx/export_stream.py:126`

```python
my_base = account.split("_6")[0] if "_6" in account else account
```

这段代码赌的是账号目录名 `wxid_xxx_<uin>` 的 uin 以 `6` 开头。真实风险比"赌前缀"更一般：`"_6"` 是任意子串匹配——wxid 本体含 `6` 开头段时（如 `wxid_6abc_6409`），`split("_6")[0]` 直接得到 `"wxid"`，is_me 全灭；uin 不以 6 开头时 `is_me` 也会失效。后果：自己发的消息气泡方向、头像、导出产物中的 `isSend` 全部错位。

**修复方向**：不要直接换成 `media.clean_wxid()`（`siwx/media.py:73-77`）——它对 `wxid_a_b_1234` 会返回 `wxid_a`，把 wxid 本身含下划线的情况切错。正确规则是前端已在用的：**只剥掉末尾纯数字段**（`chat.js:198-200` `ownerUsername()`：先以 `/^wxid_.+_\d+$/` 校验，再 `replace(/_\d+$/, '')`）。建议新建共享 helper（如 `owner_base(account)`），三处 Python 调用点统一替换，前端收敛为同一规则。注意 `clean_wxid()` 在 `siwx/strategies/mmkv.py:22-28` 还有一份近似拷贝（语义相同），且被 MMKV 密钥派生与图片路径查找依赖——**不要改它自身的语义**，新建共享 helper 正确避开了这个坑。必须补回归用例：uin 不以 6 开头、wxid 含下划线、wxid 本体含 6 开头段、自定义账号 ID（无数字后缀）。

### V-2【中】消息富化逻辑三处近乎逐行重复

**位置**：`siwx/api_chat.py:502-582`（`build_messages`）、`siwx/api_chat.py:639-695`（`/messages` 端点内联）、`siwx/export_stream.py:32-92`（`_enrich_row`）

sender 解析 / quote / link / 媒体提取七个块三处逐字相同，仅最后的 dict 组装形状不同。`api_chat.py:473` 注释称"导出与 API 共用"，但该函数实际只被 MCP 调用（`mcp_server.py:172,193`），Web API 端点并未复用——三份拷贝各服务一个消费方（MCP / Web API / 导出）。修 bug（如 V-1）需要改三处，极易漏。

**修复方向**：抽成单个 `_enrich_row()`，API 与导出都调用；API 响应不带导出专用字段（省流量）用参数控制。与 V-1 捆绑为同一改动最划算（is_me 的修复点恰好就是这三处）。

### V-3【低】分页无会话总数（`has_more` 判定本身是精确的）

**位置**：`siwx/api_chat.py:620`（每分片 `LIMIT {limit*2}`）、`:636`（`has_more = len(candidates) > limit`）

`has_more` 判定是**精确的**：若合并候选数 > limit，`candidates[-limit:]` 之外是真实存在的更旧行，`has_more=true` 正确；若 ≤ limit，则每个分片都未触及 `limit*2` 上限、已把 `create_time < before` 的行取尽，不存在更旧消息，`has_more=false` 也正确。"多分片分布不均"不构成反例（分布只影响各分片是否截断，不破坏上述两分支）。此条**无需修复**；真正缺的只有**会话总数**（无任何 COUNT，前端副标题只能显示"已载入 N 条"）。

**修复方向**：现有判定保留（改每分片 `limit+1` 只是无害的简化，并非修复）；有增量价值的仅剩每分片 `COUNT(*)`（分片索引已缓存，代价可忽略）提供总数。

### V-4【低】时间轴 / 单会话统计每请求全量聚合，无缓存

**位置**：`siwx/api_chat.py:714-766`（`/timeline`）、`:769-828`（`/stats`）

会话列表有签名缓存（`_SESSION_CACHE`），但这两个端点每次都把分片按 `strftime` 聚合一遍。适合照抄 `_SESSION_CACHE` 的"账号+会话+文件签名"缓存模式。

### V-5【低】更新后无感知

自动增量刷新完成后，正在浏览的用户不知道有新消息，须退出会话重进。低成本方案：前端轮询 `/api/job` 时比对当前会话最新 `ts`，有变化在页顶挂"有新消息，点击刷新"。

### V-6【低】"数据截至时间"与"最后更新时间"未区分

增量更新粒度是整库（微信 4.x 库整体加密，无法更细），且 WAL 不支持意味着微信运行中产生的最新消息要等 checkpoint 才进主库（`docs/wal-support-plan.md` 已论证过）。建议 UI 把两者分开显示，避免用户误以为显示实时数据。

## 五、导出环节

### E-1【高·真 bug】「每会话一个 ZIP」模式下会话级"下载文件"链接全是死链

**位置**：`siwx/exporter.py:346-350`（zip 后 `rmtree(export_dir)`）、`:363`（返回 `"file": str(out_file)`）、`:619`（`run_export_multi` 收集 `res.get("file")`）、`siwx/ui/pages/export.js:330`（渲染下载链接）

`run_export` 打包 zip 后删除整个导出目录，但返回值 `"file"` 仍指向目录内已被删除的文件。`pack="each"` 时每个会话都走 zip+删除，前端拿这个失效路径渲染"下载文件"链接 → 点击必然 404。单会话导出与"单个 ZIP"模式不受影响。MCP 入口（`mcp_server.py:261`）直接调 `run_export`，默认 `pack="single"` 不受影响，但显式传 `pack="zip"` 时同样返回死链。

**修复方向**：zip 打包后把 `file` 置空（或指向 zip 路径），前端对空值不渲染链接。

### E-2【中】聊天页"导出所选 N 条"实际导出的是所选日期的全部消息

**位置**：`siwx/ui/pages/chat.js:94-107`（所选消息 ts 按天取整为日期范围）、`siwx/server.py:385-387`（按 start/end 日期过滤）

在三天里各选 2 条消息 → 实际导出这三天**全部**消息（可能数千条）。导出页有小横幅提示"按此日期范围导出"（`export.js:36`），但语义落差容易踩。

**修复方向**：按 `localId` 列表精确导出（后端加 id 列表参数），或横幅明确写"将导出 X 日至 Y 日的全部消息，而非仅所选"。

### E-3【中】两遍扫描都在做全量富化，第一遍可砍掉约 90% 工作

**位置**：`siwx/exporter.py:80-99`（`_collect_metadata`）、`siwx/export_stream.py:112-151`（`message_stream`）

`run_export` 先跑元数据遍再跑写出遍，两遍都走 `message_stream` → 每行都执行解码、发送者前缀正则等全套富化（zstd 解压仅针对压缩内容、XML 解析仅 49/57 型）。但第一遍只需要：总数、发送者集合、图片/语音引用——后两者只需查 `WHERE local_type IN (3,34,47)` 的行；count/first_ts/last_ts/senders 甚至可完全在 SQL 侧完成，第一遍可比本方案更轻。纯文本消息（通常占大头）完全不必在第一遍富化。预计大会话导出提速 30-40%（未实测，量级可信）。

### E-4【中】HTML / TOML"流式导出"名不副实

**位置**：`siwx/exporter.py:439-472`（`_write_html_streaming`：全部消息 `lines.extend` 进内存后一次性 `render_html`）、`:486-517`（TOML 同样全量累积 `lines` 后 `write_text`）

与模块 docstring 及 README"流式处理"的宣传不符，大会话导出内存峰值高。JSON/CSV/TXT/MD 是真流式。

**修复方向**：HTML 真流式可行——`_collect_metadata` 第一遍已收集 senders（members 原料），`CHAT_DATA.messages` 数组可仿照 `IncrementalJSONWriter` 逐条写入 `<script>`，模板拆为前后两个常量。TOML 逐条 append 后立即写文件即可。属中等工作量。

### E-5【中】`</script>` 未转义，消息内容可截断/注入导出 HTML

**位置**：`siwx/html_template.py:73-79`

```python
data_json = json.dumps(chat_data, ensure_ascii=False)
... f"<script>window.CHAT_DATA = {data_json};</script>" ...
```

聊天中出现含 `</script>` 的文本即提前终止 script 标签，导出的自包含网页损坏。**修复一行**：`json.dumps(...).replace("</", "<\\/")`，正常数据零影响。两处必须一起处理：

- `<!--`：消息含 `<!--`（叠加 `<script>`）会令 HTML 解析器进入 script 双转义状态，模板真正写出的 `</script>` 闭标签被吞、整个页面照样损坏——只转义 `</` 而不顾 `<!--` 等于没修；
- U+2028/2029：仅影响旧引擎，可选项。

### E-6【中】XLSX 导出用 openpyxl 普通模式，全部行驻留内存

**位置**：`siwx/exporter.py:556-573`

8 种格式中唯一剩余的全量内存实现（HTML/TOML 改造后）。改 `Workbook(write_only=True)` 约 **2-3 行**：write_only 模式没有默认 sheet，`wb.active` 要换成 `wb.create_sheet()`，其余 `append`/`save` API 兼容。

### E-7【中】媒体跨导出无复用，失败静默

- 每次导出把会话内所有图片重新走三级来源查找 + AES 解密（`exporter.py:102-134`），即使同一张图昨天刚导出过。**修复方向**：按 md5 索引的持久化解密缓存（朋友圈 CDN 侧已有磁盘缓存先例，`sns_cdn.py`），重复导出媒体步骤几乎归零。
- 单图失败 `_try_decrypt` 裸 `except Exception: pass`（`exporter.py:178-179`），导出报告只知数量不知原因（对比 `sns_export.py:307-315` 的原因分布统计）。

### E-8【低】超长消息截断行为三种格式不一致且无提示

- HTML 嵌入截 8000：`html_template.py:40`；SQLite `rawContent` 截 8000：`exporter.py:545`；JSON 不截断。截断均无任何标记。
- **修复方向**：统一为"截断但追加省略标记"，或提高上限。

### E-9【低】TXT 头部"消息数：未知（流式导出）"

**位置**：`siwx/export_stream.py:212`。元数据遍早已统计出 count，纯属未回填。

### E-10【低】媒体文件名非内容寻址 + 导出目录累积

- 媒体命名 `{i:04d}_{md5[:12]}.jpg`（`exporter.py:113`），同一会话两次导出文件名不同；做 E-7 缓存时顺手改 md5 寻址。
- 导出目录按秒级时间戳累积（`exporter.py:239`，D-5 已知同名撞车风险），`/api/export/list` 只展示最近 30 个（`api_export.py:91`），无清理入口。
- `shutil.make_archive` 打包期间 zip 与原目录并存，大会话临时双倍磁盘占用；`rmtree(..., ignore_errors=True)` 失败会留孤儿目录（`exporter.py:348-350`）。

### E-11【低】导出页轮询全量拉日志 + 全量重画 DOM

**位置**：`siwx/server.py:729-740`（`/api/job` 每次返回最多 1200 条日志）、`siwx/ui/pages/export.js:256-289`（600ms 轮询 + 每次 `innerHTML` 全量重画）

### E-12【参照】朋友圈导出质量明显更好，可作为聊天导出重构模板

`siwx/sns_export.py` 做对了一系列聊天导出没做的事：HTML 全程 `_html.escape`（`:470-508`）、JSON 真增量写出（`:329-342`）、失败媒体带原因分布与采样日志（`:307-323`）、并发夹紧（`:37-43`）、失败可追溯不静默。**建议将这套模式反向移植到 `exporter.py`**，而不是零散打补丁。

## 六、后端任务调度与状态

### S-1【中】`/api/status` 每请求全量重扫，且三处重复计算

- `/api/status` 每次请求 `find_wechat_pids()` + 逐库 `collect_db_files()` + HMAC 验证（`server.py:545-582`），前端每 5 秒轮询（`app.js:277`），引导页 `guide.js` 也在拉——常驻磁盘 IO。
- TUI 状态栏 `_status_getter` 独立调 `find_wechat_pids()` + `find_wechat_data_dirs()`（`server.py:826-829`），且状态栏循环 **1 秒一轮**（`tui.py:172`），比前端更频。
- auto-sync 调度器每 30 秒独立 `find_wechat_pids()`（`server.py:772`）。
- **修复方向**：10~15 秒 TTL 的共享缓存，三处共用；失效点除解密任务结束外还须覆盖**手动新增数据目录**（否则引导页最长滞后一个 TTL）。风险点：微信刚启动/刚解密完时状态展示滞后最多一个 TTL，属可接受（任务执行不受影响，任务自己会重新发现）。

### S-2【低】`sync` 模式重复发现账号，且会丢弃单账号语义

`_run_job` 开头已 `find_wechat_data_dirs()` 赋 `dirs`（`server.py:279`），`sync` 分支又无条件调一遍（`server.py:354`）——每次增量同步多一次全盘扫描。更实质的隐患：若将来带 `db_dir` 调 sync，354 行会**静默丢弃**单账号语义改扫全部账号——删掉它同时消除该隐患。

### S-3【中】单任务槽、不可取消

全局一次一个任务（`server.py:161-163, 585-597`），长任务无法取消，中断只能杀进程。`_run_job` 是 220 行 if/elif（`server.py:215-434`），keys/decrypt/auto/sync 四分支有重复的"遍历账号+日志模板"。

**修复方向**：只给 export/sync 分支加协作式取消标志（高频痛点是长导出中途停不了），keys/decrypt 不值得动。

### S-4【低】auto-sync 读 `_job["ok"]` 存在 TOCTOU

`server.py:781-785`：读取本身在 `with _lock` 块内，但竞态是 TOCTOU——`_run_job` 返回（finally 释放任务槽）与 `_worker` 获锁之间的窗口内，用户可经 `/api/run` 重置 `_job`（`ok: False`），`_worker` 会把**新任务**的 ok 读成自己的结果——sync 成功被记为失败（反向几乎不可能）。只影响 auto-sync 结果标记/提示文案，不影响数据，风险低。

### S-5【低】未捕获异常返回完整 traceback 给页面

`server.py:194`。本地单用户威胁模型下不算漏洞，但配合 DNS rebinding（既有审计 M-1）会放大信息泄露；**若将来允许 `--host 0.0.0.0`，必须先收掉**（连同既有审计的 H-1/H-2/M-2/M-3）。

### S-6【低】前端任务轮询逻辑四处重复

`common.js:45-74`（`startJob`）、`chat.js:60-68`（写死 300 次×1s，超时后静默放弃且无提示）、`export.js:256-280`、`sns.js:723-742` 各自实现 `/api/job` 轮询。行为不一致（chat 页同步超 5 分钟无提示）。**修复方向**：统一走 `SX.startJob`——注意 `startJob` 目前节拍（固定 600ms）与超时策略（**无超时**）均不可配，需先加 `interval`/`timeout` 选项再收敛；且 chat 页现有的 5 分钟兜底统一后会变成无限轮询，须显式补超时与超时提示。

## 七、前端基础设施与各页

### F-1【高·结构性隐患】`SX.esc()` 不转义引号

**位置**：`siwx/ui/common.js:3-7`

```js
function esc(s) {
  const d = document.createElement('div');
  d.textContent = s == null ? '' : String(s);
  return d.innerHTML;      // 序列化只转义 & < >，不转义 " 和 '
}
```

该函数被大量用于**属性位置**：`data-u="${esc(s.username)}"`（`chat.js:214`）、`data-key="${esc(msgKey(m))}"`（`chat.js:455`）、`onclick="SX.openPath('${esc(r.total_dir)}')"`（`export.js:317`）等数十处——全 ui 目录 `${esc(` 插值共 112 处，其中相当部分位于属性位。值中一旦出现引号即可逃出属性注入任意属性/事件。两个现实问题：

- **(a) 现存功能 bug**——`settings.js:140` 的 `data-choices="${esc(JSON.stringify(it.choices || []))}"`，JSON 输出必然含引号，属性被截断，`settings.js:234` 的 `JSON.parse` 抛错被静默吞掉，插件 choice 型设置项的下拉选项**现在就在丢失**；
- **(b) 远端输入已进属性位**——`chat.js:422` 的 `<a href="${esc(full)}">`，`full` 来自联系人发来的链接消息（`m.link.url`，解析自远端 XML），"各字段字符集恰好干净"的前提对它不成立。其余字段（wxid、消息 key、服务器生成路径）目前确实干净——安全边界仍是"新增字段随时破防"。

**修复一行**：`esc()` 内把 `"` → `&quot;`、`'` → `&#39;`。属性位置的转义从此与文本位置同样安全。已核查全 ui 目录无依赖 esc 输出再反转义的代码，改动无回归风险，且 settings.js 的选项丢失 bug 随之修复——此项应尽快做。

### F-2【中】页面模块 import 每次导航都失效缓存

**位置**：`siwx/ui/app.js:156`

```js
const mod = await import(`${base.js}?v=${Date.now()}`);
```

每次导航时间戳变化，来回切页每次都重新下载、重新解析执行 chat.js 这种 600 行模块。同文件 CSS 用的却是固定 `UI_VERSION` 常量（`app.js:32`）。**修复**：统一 `?v=${UI_VERSION}`。注意两点：

- **单改前端不够**——`server.py` 静态服务全是 `send_from_directory`，无任何 `Cache-Control` 配置（`:490-525`），固定 URL 后软件更新覆盖文件时浏览器可能仍用启发式缓存，出现"更新后不生效"；需配套给静态路由加 `Cache-Control: no-cache`（保留 ETag 协商）。
- `chat.js:2`、`export.js:2` 硬编码了 `'/widgets.js?v=2026100203'`，手工升 `UI_VERSION` 时不会自动跟随，统一时要一并处理。

### F-3【中】壳层路由与聊天跳转同款的竞态

`navigate()` 是 async 且无序号守卫（`app.js:107-163`），快速连点两个菜单项，慢的加载流程后完成会把**旧页面**渲染上去。与 J-2 同类，可用同一"代数守卫"模式一起修。

### F-4【低】导出页不恢复运行中状态

切走再切回导出页，`destroy()` 清了轮询（`export.js:346-348`），`init()` 不检查后台任务——按钮显示可用，点击才 409"已有任务在运行"。**修复**：`init` 先拉一次 `/api/job`，`running && mode==='export'` 时恢复进度面板。

### F-5【低】体验杂项（一致性）

## 九、Rust 迁移评估（已决策：不迁移）

经评估，迁移难度分层如下，结论是**不做整体重写**（用户决策，2026-10-02）：

| 分层 | 内容 | 迁移难度 |
|---|---|---|
| 容易 | SQLCipher 解密内核（纯 Python + pycryptodome）、ISAAC64（139 行零依赖）、CDN 下载、MMKV 离线解析 | 低，Rust 直译且更快 |
| 中等 | Windows 内存读取（ctypes 手写）、DPAPI、MCP stdio JSON-RPC（764 行）、~60 个 Flask 端点（前端纯静态可原样保留） | 中 |
| 受阻 | **插件系统**（importlib 动态加载 + 18 类 hook（`contract.py:21-40` `HOOK_KEYS`）+ Blueprint 注入，迁移即插件生态作废）、pilk/SILK 解码（Rust 无成熟 crate，可子进程绕过） | 结构性障碍 |

**不做迁移的理由**：性能痛点（解密吞吐）只占链路一小部分；工程质量本身高于同类平均，重写性价比低；插件生态是死结。若将来确需性能，可只将解密内核/导出管线编译为 Python 可调用扩展（渐进式），而非全栈重写。
